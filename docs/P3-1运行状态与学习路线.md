# P3-1：显式阶段流与统一终止原因

2026-09-23。本次从 `8809f0b` 继续，复用现有问答链路和论文工作台。暂停评测/人工审阅工具扩展，24 题人工标注不是核心开发前提。P2B 质量问题保留；P3-1 工程完成不等于 P3 全部完成，也不等于真实回答质量提高。

## 1. 先理解已有链路

```text
工作台选择论文、提交问题
  → API 参数校验与单进程并发门
  → retrieve：指定论文检索、数据库事实回查、可选重排
  → context：按完整段落选择上下文、配置和证据快照检查
  → generate：生成结构化草稿
  → citation_check：引用 ID、非空摘录、原文连续匹配
  → verify：模型判断逐条支持关系及是否回答问题
  → publication_check：复查论文版本、语料 revision 和正文哈希
  → publish：发布同一份已核验草稿
```

这是 Python 控制的固定工作流，模型只负责生成与语义核验两个节点。它没有自行规划或任意调用工具，不能称为自主多 Agent。QASPER 标准答案继续只供离线评测，不进入上述链路。

| 能力 | 盘点结果 |
|---|---|
| 论文范围、事实回查、严格输出 schema、引用硬检查、语义核验、发布前版本复查 | P2B 已有，本次复用 |
| 检索配置与耗时、上下文 included/skipped、调用 usage、证据/草稿/输出哈希 | P2B 已有，本次不另建记录系统 |
| 同进程互斥锁、最多两次生成/核验请求、无模型自动重试 | P2B 已有；不是跨进程并发/配额控制 |
| 24,000 Unicode 字符上下文限制、HTTP 连接/读写超时 | P2B 已有；不是 token/金额预算，也不是整个任务截止时间 |
| 阶段顺序、细分终止原因、HTTP 失败的阶段/调用记录 | 本次补齐到请求内与响应中 |
| 在线运行持久化、崩溃恢复、整体截止时间、服务端取消、可配置预算、身份鉴权 | 尚未实现；单篇过滤不等于多租户权限 |

## 2. 一个小增量解决什么

以前 `evidence_insufficient` 同时表示检索没找到证据、字符预算未纳入任何段落和生成器主动弃答；`verification_failed` 同时表示引用不合法和语义不支持。生成后版本变化会返回 HTTP 409，但此前的调用记录不会返回。

现在保留原 `status`、HTTP 状态码、`generation` 和检索 `trace`，增加 `run`。正常结果的 `run.trace_id` 复用原检索 ID；检索返回之前就失败时也生成 ID。HTTP 失败携带 `run`，若已进入生成流程还携带原有 `generation` 摘要，保留已完成调用的耗时、usage 和哈希，不携带草稿或原文。

```json
{
  "state": "blocked",
  "reason": "semantic_verification_failed",
  "terminal_stage": "verify",
  "stages": [
    {"name": "verify", "status": "stopped", "latency_ms": 12.3},
    {"name": "publication_check", "status": "not_run", "latency_ms": null},
    {"name": "publish", "status": "not_run", "latency_ms": null}
  ]
}
```

上面是省略其他字段和阶段的契约示意，时间为示意值。完整记录始终列出七个阶段；没执行的阶段为 `not_run/null`，不能显示成通过或零耗时。

| 终态 | 常见 reason | 含义 |
|---|---|---|
| completed | published | 流程允许发布；不保证模型判断正确 |
| abstained | no_retrieved_evidence / context_budget_excluded_all / generator_abstained | 本次不作答；不证明整篇论文无法回答 |
| blocked | citation_invalid / semantic_verification_failed / corpus_changed / evidence_integrity_failed / model_refused | 被检查或模型拒绝所阻止；不对真实答案正确性作独立裁定 |
| failed | generation_not_configured / provider_timeout / invalid_output 等 | 配置、依赖或技术失败；不能计为正确拒答 |

`terminal_stage` 是流程最终停留处。生成器弃答仍沿用原有发布前版本复查，因此最终停在 `publication_check`，reason 为 `generator_abstained`；引用检查和语义核验未执行，`publish` 也未执行。前端展示每个阶段的完成/终止状态及耗时。

`harness.py` 限定合法阶段边；从生成弃答支路进入版本复查后，不能绕过引用和语义检查直接进入发布。结束后不能重新进入阶段或第二次结束。业务 gate 继续复用 `generation.py`，不再实现第二套核验器。

工作台的“运行记录”在响应到达后显示，HTTP 409/502 等失败也能查看。切换论文、切换任务和新请求会清除旧记录。它不是实时进度或运行历史数据库；浏览器停止等待也不保证后端或远端停止计费。参数校验、并发拒绝等在受理前发生的错误没有 run。

## 4. 阅读顺序与简历技术点

1. 读 `service.py` 的 `retrieve`：候选排序和返回事实分开，原文回查约束证据来源。Trace 能帮助定位，不代表召回正确。
2. 读 `generation.py` 的 `_answer`：引用摘录存在只是硬约束；语义支持要看判定结果，但模型可能误判。注意所有失败分支都不返回草稿。
3. 读 `harness.py` 的 `enter/finish`：显式状态机把合法顺序和终态放在模型外部。单纯增加日志字段不会自动获得控制能力，所以还要拒绝越过 gate 的阶段迁移。
4. 读 `tests/test_harness.py`：模拟模型超时、非法引用、语义不通过、版本变化，观察调用次数、未执行阶段与空 claims。测试证明程序对给定信号的行为，不能证明模型对真实论文的判断质量。
5. 在原工作台查看一次“运行记录”：先找 reason 和终止阶段，再看原 `generation.calls` 与检查字段。先定位检索、生成、核验还是版本问题，再决定下一次改哪里。

可准确表述为：“在证据问答工作流中实现显式阶段约束、统一终止原因和故障路径记录，复用引用与版本校验，验证未通过门禁的草稿不发布。”目前不能写成“完整生产级 Harness”“端到端预算治理”或“已解决幻觉”。面试题已留在根目录题库，本次不启动面试。
