# P2B-2：交叉编码器重排与六组消融

2026-09-22。P2B-2 工程验收通过。工程验收和用户学习验收分开；本增量不包含生成答案、支持关系核验或拒答。

## 交付与模型选择

工作台增加默认关闭的“模型重排”开关，可以配合 BM25、向量或混合检索使用。后端取同一检索方式前 20 个候选，先回查当前数据库正文，再让本地交叉编码器逐对阅读问题和正文窗口，按分数重新排序返回前五。用户选择超过 20 条结果时，候选上限随 top-k 增加，最多 50。

选择 `cross-encoder/ms-marco-MiniLM-L6-v2` 六层英文模型（本次 safetensors 约 86.7 MiB），固定 revision 与每个模型文件的 SHA-256。它在 MS MARCO 段落排序任务上训练，适合作为当前英文检索的轻量起点；这不保证在 NLP 论文上优于其他模型。BGE-reranker-base 等更大/多语言模型属于另一个资源与质量对照，不为了增加组件而先全部引入。原有 Transformers/PyTorch 依赖即可运行，无新增按量 API 费用，也不需要重建已有 BGE 向量。[官方模型卡](https://huggingface.co/cross-encoder/ms-marco-MiniLM-L6-v2)

这里的两个模型职责不同：BGE 独立编码问题和段落，正文向量可以提前保存；交叉编码器对问题和候选正文联合计算，换一个问题通常就要重新评分。它适合少量候选精排，不适合每次将全库逐段读一遍。模型输出是原始 logit，可为负数，不是正确概率或已校准置信度。

## 长输入与失败边界

最大长度 512 token 包含问题、正文和三个特殊 token。问题不加 BGE 前缀，最多 128 token，超限明确返回 422；正文使用剩余预算滑窗，重叠 64 token，保留尾部，每段取最高窗口分数。这样避免只看长段落开头，但会增加运算并可能偏向多窗口段落。每次最多 256 个窗口，超限拒绝本次重排，不静默丢尾部。

在线模型只加载本地 safetensors，校验随包发布的固定文件哈希，不开启远程模型代码。文件缺失、损坏、设备失败或无效分数时返回 503；用户可以关闭开关继续原有检索，系统不会自动把未重排的结果标成重排成功。

所有候选在模型调用前检查论文范围、正文哈希和当前版本。模型只能返回与候选对应的分数，不能添加证据 ID。推理后再检查语料 revision；发生变化就重试整条检索，连续变化则返回 409。普通未命中仍不能等同于正确拒答。当前没有模型推理硬超时、独立 worker 或并发 SLA，浏览器取消只停止等待，不保证中断本地计算。

## 公平比较的协议

沿用 P2B-1 冻结的 745 道 dev 文本证据题及相同文件哈希，无重排三组必须逐题复现之前 top-5 排名。重排三组分别取各自前 20 个候选；混合为两路各取 20、RRF 合并后保留 20，而非把最多 40 个并集候选全部交给模型。

除了 Hit@5、证据 Recall@5、MRR@5，还报告每组候选 Hit@20、Recall@20，及开启重排后的新增/丢失命中。候选不含 gold 的题目属于召回限制；候选含 gold 但重排前五没有，则是当前排序仍未解决的部分。这种自动归类只根据标注证据，不等于人工诊断了模型失败原因。

评测采用 CPU 批量问题向量以复现 P2B-1；重排在 MPS 上逐题逐组真实执行，不缓存三组共享候选的分数。报告记录编码批量耗时、每组重排延迟分布和模型首次加载成本。它不是端到端并发性能报告，不能用模型卡 V100 吞吐代替本机测试。

参数已写入 [检索实验协议](P2B检索实验协议.md) 后才运行完整实验；不使用官方 test，不微调，也不根据这一轮分数追加隐式参数搜索。

## 复现

先完成 P2B-1 的依赖、正文入库和向量构建，然后从项目根目录运行：

```bash
.venv/bin/python scripts/prepare_reranker_model.py
.venv/bin/python scripts/evaluate_reranker.py --device mps
RUN_STORAGE_INTEGRATION=1 .venv/bin/python -m pytest -q
npm --prefix frontend test
npm --prefix frontend run build
.venv/bin/python scripts/run_api.py
```

首次准备脚本需要网络，权重保存在忽略的 `.local/models/`。其他设备可用 `--device cpu`；API 默认 CPU，可设置 `RESEARCH_RERANKER_DEVICE=mps`。设备可能带来细小数值差异，报告会记录实际设备。新参数 `rerank` 默认为 false，旧 API 请求保持原行为：

```json
{"paper_id":"1503.00841","query":"What methods are proposed to improve robustness?","top_k":5,"mode":"hybrid","rerank":true}
```

响应仍是 `evidence_only`；`trace.rerank_candidates` 记录评分前的候选顺序，`candidate_rank`/`candidate_score` 保留每条返回结果的原排序，`score` 是重排后的分数。Trace 包含模型配置、设备、窗口数量、批次数和耗时。返回完整正文供阅读，模型实际读取的输入受上述窗口协议约束。

## 全量实测结果

冻结的 745 道 dev 文本证据题，三个无重排组逐题与 P2B-1 排名一致，差异 0。参数未在看到结果后追加调整。完整逐题报告：[六组重排消融](../reports/p2b_reranker_dev.json)。

| 方式 | Hit@5 | 证据 Recall@5 | MRR@5 |
|---|---|---|---|
| BM25 | 58.52% | 50.64% | 0.3330 |
| BM25 + 重排 | 70.60% | 62.47% | 0.4547 |
| 向量 | 66.17% | 58.23% | 0.4170 |
| 向量 + 重排 | 74.09% | 65.38% | 0.4808 |
| 混合 RRF | 65.91% | 58.11% | 0.4148 |
| 混合 RRF + 重排 | 73.29% | 64.73% | 0.4710 |

| 召回方式 | 候选 Hit@20 | 重排新增 / 丢失命中题数 | 候选未命中题数 | 候选命中但重排前五未命中 |
|---|---|---|---|---|
| BM25 | 89.40% | 125 / 35 | 79 | 140 |
| 向量 | 94.36% | 108 / 49 | 42 | 151 |
| 混合 RRF | 95.17% | 101 / 46 | 36 | 163 |

向量 + 重排在本轮前五指标最高；混合候选覆盖率更高，却在重排时丢掉更多已有候选证据。这支持继续分析候选组成和精排错误，不能简单断言“混合加重排永远更好”，也不构成不同模型间的普遍排名。六组均保留，页面默认检索方式与重排开关不自动更改。

MPS 单进程评测耗时 424.53 秒。三个组的重排耗时中位数约 84–86 ms，P95 约 141–146 ms；它只包含该步骤，不包含完整在线请求。批量问题编码使用 CPU（含加载 3.34 秒），与默认 CPU 在线重排样例的计时口径和设备不同。未做并发压测，也未报告统计显著性。

## 学习顺序

1. 沿 `api.py → service.py → reranking.py` 跟踪 `rerank=true`，说明为什么先回查事实、再调用模型、最后再检查版本。
2. 手算 128 token 问题时剩余正文预算，检查 `pair_windows` 的 token 类型标记与尾部覆盖；解释为什么不能直接复用 BGE 的 510-token 正文窗口。
3. 查看一次三组候选与重排结果，解释候选数、返回数、候选分数与重排分数各是什么。
4. 用六组报告区分召回上限和精排损失，再查看新增与丢失命中的具体 question_id；不要只挑成功样例。
5. 观察缺失模型、超长问题和换版测试，解释可恢复错误和 fail-closed；再讨论分离 worker、超时与取消需要哪些额外机制。
