## 用户流程

已发布回答下方提供“有帮助 / 存在问题”和可选说明（最多 2000 字符），默认不勾选。提交前明确说明将保存本次问题、已发布回答、引用定位和反馈。保存后可以修改；刷新页面后，在“当前论文的最近运行”中打开对应记录，再展开“查看或修改这次运行的反馈”。

历史反馈同时展示当时的问题、回答、引用及论文版本。普通运行历史仍只存元数据；未提交反馈的历史运行没有答案全文，页面明确说明无法还原，不用草稿冒充。失败、拦截、未作答的运行不提供答案评价；升级前未绑定指纹的旧回答也不能补造快照。

## 最小实现与数据边界

```text
原问答：检索 → 生成 → 引用检查 → 语义核验 → 发布前复查
                                                   ↓
发布：构造最终回答快照 → 保存快照指纹到运行终态 → 返回回答和快照
                                                   ↓ 用户明确提交反馈
POST /runs/{run_id}/feedback：检查所有者与论文权限 → 校验快照指纹
                             → 检查反馈版本 → 保存反馈及快照
GET /runs/{run_id}/feedback：检查所有者与当前权限 → 返回已保存反馈
```

快照包含 run_id、论文 ID、问题、最终结构化回答、提示词版本、语言，以及引用段落的 ID、来源、版本、章节/段落序号和正文 SHA-256。保存引用短句，但不复制整段正文。可选修正发生时，绑定重新核验后的最终回答。`feedback.py` 统一构造和计算规范 JSON 的 SHA-256；`generation.py` 在发布终态前保存 `feedback_sha256`，只有发布成功后才返回快照。

客户端提交完整快照，服务端与不可变的运行终态中的指纹比较。用户改写问题、回答、引用版本或 run_id 均会被拒绝。指纹不是正确性证明，也不是对客户端签名；可信来源是服务端保存的运行记录。它解决的是“评价对象有没有被替换”。

`006_answer_feedback.sql` 在原 PostgreSQL 增加一张表，每次运行只有一条当前反馈，关联 `answer_runs`；不新增数据库服务。运行记录不保存答案全文，只有明确提交反馈时才保存快照。目标快照不可修改，评价及说明可修改，版本递增。当前仅保留最新反馈，不保留每次编辑内容的审计历史，也未增加删除/撤回入口。

读写沿用运行所有者和当前论文授权，响应不缓存。凭证或论文变化时，前端终止旧读取并忽略迟到响应；撤权后隐藏反馈正文。文件授权与数据库提交不是同一事务：写入前后分别复查，若在写入期间撤权，写入可能已完成，但响应不会再返回内容。默认 local_public 使用共享身份，不构成多用户私有反馈；Memory 模式仅进程内保存，重启恢复需要 PostgreSQL。

## 版本检查与重试

首次提交携带 expected_revision=0；读取到版本 1 后修改，携带 expected_revision=1。只有当前版本匹配才允许变更，否则返回 409。页面保留编辑内容并暂停提交，用户点击“重新读取已保存反馈（替换当前编辑）”后再修改。这是乐观并发控制，防止多个页面静默覆盖。

相同目标、评价和说明的重复提交直接返回当前记录，不增加版本。这允许“服务端已保存但响应丢失”后的安全重试；如果其他页面已经改成不同内容，旧版本仍被拒绝。保存未确认时，页面不能直接断言写入失败。数据库通过唯一键和带版本条件的更新再做约束；继续遵守 P3 单 worker 的运行存储边界。

反馈说明作为数据存储，以 React 文本方式展示，不作为 HTML 执行，也不进入后续模型上下文。用户点赞不等于正确、点踩也不自动定位失败节点；没有新增策略自动调整或质量标签。

## 接口与运行

- `GET /api/v1/runs/{run_id}/feedback`：返回 feedback 对象，尚未提交时为 null。
- `POST /api/v1/runs/{run_id}/feedback`：rating 为 helpful/problem，note 可选，expected_revision 为非负整数，target 为服务器返回的反馈快照；额外字段拒绝。
- 成功返回当前反馈、版本、创建/更新时间和目标快照。快照不匹配或编辑冲突为 409；无权访问沿用原 401/403/404 边界，存储故障为 503。

## 学习顺序与简历技术点

先沿 `generation.py` 的发布逻辑看最终快照，再读 `feedback.py` 的 next_feedback，最后对照 `run_store.py` 和 `AnswerFeedback.tsx` 的版本检查与错误恢复。

需要掌握三个区别：run_id 标识一次运行，指纹约束这次运行发布的具体内容，revision 控制反馈修改顺序。把反馈挂到 run_id 上还不够，因为客户端可能带来不同的答案；只有指纹也不够，因为它不处理并发编辑；这些机制都不能证明模型答案正确。

可据实表述为：“实现关联已发布回答快照的用户反馈，复用运行权限与 PostgreSQL，使用内容指纹防止评价对象替换、乐观并发控制避免覆盖，并支持历史追溯。”不能表述为已完成自动反馈学习、完整编辑审计、模型准确率提升或多租户生产部署。
